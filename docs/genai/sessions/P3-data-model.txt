⏺ Before I write anything, here are the open design decisions I see, each with
  my recommendation. The repo already has the Spring Boot 3.5.16 skeleton,
  Flyway with an empty db/migration, ddl-auto: validate, dev and test profiles,
  and a Testcontainers smoke test.

  D1 – Waitlist. None. Registration stays CONFIRMED|CANCELLED and capacity is a
  hard limit. A waitlist can come later in a new migration.

  D2 – Location. A free-text column (VARCHAR(255)). A separate table adds joins
  without giving any workflow something it needs.

  D3 – Category. A Java enum stored as VARCHAR with a CHECK: ACADEMIC, CAREER, 
  CULTURAL, SOCIAL, SPORTS, VOLUNTEERING, WORKSHOP, OTHER.

  D4 – Deletes.
  - Users, organizations and events with history are never hard-deleted. The FKs
    use RESTRICT, and events get the CANCELLED status instead.
  - Deleting an event cascades to its registrations, tasks and announcements. In
    practice that only happens to a DRAFT.
  - Deleting a membership sets the task's assignee to NULL, so the task becomes
    unassigned.

  D5 – Seed mechanism. A Flyway repeatable migration, R__dev_seed.sql, in a
  separate folder, classpath:db/seed-dev. Only application-dev.yml adds that
  folder, so the test and prod profiles never see it.
  - Inserts are idempotent (ON CONFLICT DO NOTHING).
  - The BCrypt hash of "password" is computed once and written into the file.
  - Event dates are relative to now(), so each status looks realistic.

  D6 – IDs and types.
  - IDs: BIGINT GENERATED BY DEFAULT AS IDENTITY.
  - Timestamps: TIMESTAMPTZ mapped to Instant.
  - All enums: VARCHAR plus a CHECK, mapped with EnumType.STRING. Native
    Postgres enums are painful to change.

  D7 – Case-insensitive uniqueness. Unique indexes on lower(email) and
  lower(organizations.name).

  D8 – Capacity and deadline.
  - capacity is NOT NULL and > 0.
  - registration_deadline is nullable (NULL means "until start") with CHECK 
    registration_deadline <= start_at.
  - The "confirmed count ≤ capacity" rule is enforced later in the service
    layer, with a row lock. A database constraint can't express it simply.

  D9 – One CONFIRMED registration. A partial unique index (event_id, user_id) 
  WHERE status='CONFIRMED'. Re-registering after a cancellation creates a new
  row, which keeps the history.

  D10 – Cross-table rules not enforced in the database. "The task assignee
  belongs to the event's organization" and "status matches the dates" are both
  left to the services, and documented in data-model.md.

  D11 – Optimistic locking. A version column on events only, since events are
  edited at the same time as people register for them.

  D12 – Tests. Add one Testcontainers test, DataModelConstraintsTest. It checks
  that the key constraints reject bad data: the partial unique index, the
  capacity CHECK and the end > start CHECK. The existing smoke test already
  checks that the schema matches the entities.

     Entities + repositories (feature packages, entity / repository 
     sub-packages)

     - user: User, GlobalRole, UserRepository (findByEmailIgnoreCase,
       existsByEmailIgnoreCase)
     - organization: Organization, OrganizationMembership, OrganizationRole;
       OrganizationRepository, OrganizationMembershipRepository
       (findByUserIdAndOrganizationId, findByOrganizationId)
     - event: Event, EventStatus, EventCategory; EventRepository
       (findByOrganizationId, findByStatus...). JpaSpecificationExecutor is left
       for W3.
     - registration: Registration, RegistrationStatus; RegistrationRepository
       (countByEventIdAndStatus, findByEventIdAndUserIdAndStatus)
     - organizing: EventTask, TaskStatus, Announcement; EventTaskRepository,
       AnnouncementRepository
     - Style: @ManyToOne(fetch = LAZY, optional = …), no bidirectional
       collections. Protected no-arg constructor plus a public constructor for
       required fields, with getters and the needed setters. No Lombok, because
       it isn't in the pom. @CreationTimestamp/@UpdateTimestamp are not used;
       created_at is set with Instant.now() in the constructor or by
       @PrePersist.
     - Cross-feature entity references (Event→Organization,
       Registration→Event/User) are JPA associations. They are allowed inside
       the persistence layer. The rule about cross-feature access going through
       services applies to services.
